● The script works for the basic case. It mostly needs fail-fast checks and the
  logging required by the project conventions in CLAUDE.md. Here are the top 5,
  most important first:

  1. Create the output dir with mkdir -p "$output_dir" before running Trim
     Galore. Trim Galore can't be relied on to create nested paths like
     results/trimgalore when results/ doesn't exist yet, and the project
     conventions require mkdir -p.
  2. Add a # Usage: line and check the argument count. With set -u, a missing
     argument currently fails with an unhelpful $2: unbound variable, while a
     check like if [[ $# -ne 3 ]]; then echo "Usage: ..." >&2; exit 1; fi tells
     the user exactly what to pass. The usage line is also required by the
     conventions.
  3. Check that both input files exist ([[ -f "$r1_fastq" ]], etc.) and that R1
     and R2 are different files. A typo or wrong path would otherwise surface
     only after the container is pulled, as a less obvious Trim Galore error,
     and swapped or duplicated inputs would silently give wrong output.
  4. Make the logging match the conventions. At the start, report the script
     name ($0) and date. At the end, report the program version (apptainer exec
     "$CONTAINER" trim_galore --version) and date. This makes SLURM logs
     traceable and records the exact software version used.
  5. Rename container to uppercase CONTAINER. It's a constant, and the
     conventions reserve uppercase for constants, so the name signals that it's
     fixed config rather than an input.

  A smaller point: --fastqc writes the FastQC reports into the same directory as
  the trimmed FASTQs. If you'd rather keep them in their own subdir of
  results/, you could add --fastqc_args "--outdir ...".
